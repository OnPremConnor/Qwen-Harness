Inside FastAPI: JSON becomes Python objects

no network traffic

schemas/chat_request.py line 8 (content: str), then routes/chat.py lines 14–21.

request          →  a ChatRequest object FastAPI built from the JSON
request.content  →  "In one sentence, what is a hash map?"
question = request.content.strip()   # routes/chat.py line 16

Python detail: request.content has no parentheses, so it is an attribute, a value stored on the object. .strip() has parentheses, so it is a method, and Python passes the string in front of the dot in as self. request.content.strip() does the same work as str.strip(request.content). Here strip() removed nothing, because the question had no extra spaces. The result is stored in question, not content, because this same function later holds the model's reply in a variable named content (line 25), and one variable cannot hold both texts.

Reading return ChatResponse(content=content) left to right: ChatResponse is a class (a blueprint). Writing a class name followed by parentheses calls it, which builds one object, the same way Dog("Rex") built rex. Inside the parentheses, name=value is a keyword argument: the name on the left belongs to the class, and the value on the right is the variable. return then hands the finished object to FastAPI, which writes it as JSON using the class's field names as keys. This line is not a function taking in a variable: the function is answer_question(request), and its only parameter is request.

Both replies are HTTP status 422, but they come from two different places. The first is the ChatRequest class rejecting a body without the key content (see "loc":["body","content"]: the class's own field name), before answer_question() even starts. The second is your own if not question: and raise HTTPException(status_code=422, …) at routes/chat.py lines 19–21, which runs only after the class accepted the body. This is how the keyword raise changes what the whole system does: it stops the function and becomes an HTTP error the browser sees.

Why one name, content, from end to end
  • The reason: the code can be read against vLLM's own documentation and names, without keeping a glossary of invented names.
  • The trade-off to know: the word no longer says which direction the text is travelling. The path in front of it does. choices[0].message.content is text coming in from the model. ChatResponse(content=…) and result.content are text going out to the browser. Read the path, not just the word.
  • Both directions use it: the browser sends {"content": …} in (ChatRequest) and receives {"content": …} back (ChatResponse), the same word vLLM uses in its own request and reply. Which class you are looking at says which way the text is going.
  • One consequence: inside answer_question(), which handles both texts, the incoming text is named question and the reply is named content. Giving both the same variable name would make the reply overwrite the question.

Where the time went

The same question, three times. "Waiting for vLLM" is the time httpx.post took inside FastAPI. "Everything else" is the whole curl time minus that.

First request after startup (cold start, recorded before the rename)34.009 seconds (waiting for vLLM) + 0.027 seconds (everything else) = 34.036 seconds (curl total)

84 tokens (completion, of which 40 tokens were thinking) ÷ 34.009 seconds = 2.47 tokens per second (overall speed)

Second request, same question (recorded before the rename)6.784 seconds (waiting for vLLM) + 0.005 seconds (everything else) = 6.789 seconds (curl total)

112 tokens (completion, of which 64 tokens were thinking) ÷ 6.784 seconds = 16.51 tokens per second (overall speed)

Third request, same question (the current code, recorded after the renames)7.925 seconds (waiting for vLLM) + 0.010 seconds (everything else) = 7.935 seconds (curl total)

105 tokens (completion, of which 61 tokens were thinking) ÷ 7.925 seconds = 13.25 tokens per second (overall speed)

Everything except the model (FastAPI, JSON parsing and curl) took 0.005 to 0.027 seconds in the three runs. The model is where the time goes. The first request took 34.009 seconds (first) ÷ 6.784 seconds (second) = 5.01 (ratio, no unit) times as long as the second. I did not find out why the first request was slower. A candidate, untested, is one-time setup inside vLLM on its first request. A test would be to restart the container and time two identical requests in a row.
