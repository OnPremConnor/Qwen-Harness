answer= (left of the =)routes/chat.py:31A keyword argument name. It tells the class which of its fields you are filling in, so it must match a field name exactly.

Reading return ChatResponse(answer=answer) left to right: ChatResponse is a class (a blueprint). Writing a class name followed by parentheses calls it, which builds one object, the same way Dog("Rex") built rex. Inside the parentheses, name=value is a keyword argument. return then hands the finished object to FastAPI, which writes it as JSON using the class's field names as keys. This line is not a function taking in a variable: the function is answer_question(request), and its only parameter is request.

Both replies are HTTP status 422, but they come from two different places. The first is the ChatRequest class rejecting a body without the key message, before answer_question() even starts. The second is your own if not message: and raise HTTPException(status_code=422, …) at routes/chat.py lines 19–21, which runs only after the class accepted the body. This is how the keyword raise changes what the whole system does: it stops the function and becomes an HTTP error the browser sees.

Why does the code rename content to answer? It is a design choice, not a Python rule; keeping content would work.
  • One word, two directions. In vLLM's format your question is messages[0].content (step 3) and the model's reply is choices[0].message.content (step 4). At your own /chat boundary the two directions get two names, message in and answer out.
  • Your contract versus theirs (my design opinion). /chat is yours; vLLM's reply format is vLLM's. If you swap the engine or add a hosted model that puts its text somewhere else, only get_qwen_answer() has to change, and the browser keeps receiving {"answer": …}.
  • The cost. One more name to track for the same text, which is the confusion you described. If that cost outweighs the benefit for you right now, using content end to end is a legitimate choice.

84 tokens (completion) ÷ 34.009 seconds = 2.47 tokens per second (overall speed)

Second request, same question6.784 seconds (waiting for vLLM) + 0.005 seconds (everything else) = 6.789 seconds (curl total)

112 tokens (completion, of which 64 tokens were thinking) ÷ 6.784 seconds = 16.51 tokens per second (overall speed)

Everything except the model (FastAPI, JSON parsing and curl) took 0.027 seconds in the first run and 0.005 seconds in the second. The model is where the time goes. The first request was about 5 times slower than the second; I did not find out why. A candidate, untested, is one-time setup inside vLLM on its first request. A test would be to restart the container and time two identical requests in a row.
